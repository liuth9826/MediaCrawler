# 穿搭趋势分析 SDD

> 状态：已批准（GATE 1，2026-09-28）
> 本文档是需求固化产物。上游需求由用户以自然语言给出，经 GATE 1 确认后冻结于此。

## 1. 目标

基于本项目已有的采集能力，自动发现高传播的穿搭帖子与博主，采集信息并做内容分析，产出穿搭趋势。

## 2. 需求

| # | 需求 | 落点 |
|---|------|------|
| R1 | 自动发现：自动搜索穿搭相关内容；以综合传播/互动表现（转发、点赞、收藏、评论）为主要挑选标准；对象同时覆盖帖子与博主 | 切片 1（帖子）、切片 2（博主） |
| R2 | 信息采集：采集帖子正文、标签、图片与互动数据，以及博主身份与作品信息 | 切片 1（帖子）、切片 2（博主） |
| R3 | 内容分析：识别穿搭的风格、元素与搭配方式，并结合互动数据判断什么在流行、为什么流行 | 切片 3/4/5 |
| R4 | 趋势产出：给出热门风格、上升中的风格，以及有代表性的帖子与博主 | 切片 4/6 |
| R5 | 结构化沉淀：结果持久化，支持增量累积与重复运行，同一内容不重复分析 | 切片 1/3 |
| R6 | 可降级、可复跑：模型或数据不齐时先采集存档，可稍后补分析；报告能脱离模型单独重建 | 切片 3/6 |
| R7 | 可定时：支持每日自动运行 | **已推迟**（用户决定暂不做） |

## 3. 边界

- 暂不做 WebUI 接入。

## 4. 质量底线（三条硬约束）

### Q1 不臆造：无图片证据不下风格结论

**实现方式**：结论必须携带证据等级，由数据结构强制，而非依靠自觉。

- `evidence_level = text_only`：仅由标签/正文/词表推出。**不得**表述为风格结论。
- `evidence_level = image_backed`：模型确实读取过图片。

报告分区展示两类结论。校验器拒绝任何 `image_backed` 但无图片引用的结论。

### Q2 可信度可判定：区分「整批不完整」与「个别失败」

**实现方式**：`trend_crawl_run` 记录每次运行的完整度。

- 记录：退出码、采集前后条目数、新增/更新数、错误行数、错误样本、运行状态。
- `status` 如实反映采集结果：采集失败/超时/子进程起不来 → `failed`，不得写成 `succeeded`。
- `confidence = low` 当且仅当：退出码非 0、或库内无任何条目、或关键词零匹配、或错误率超阈值。
- 例外：爬虫报告搜索结果**取尽**时，错误行只作明细、不判 low —— 批次范围由平台决定、
  不是被失败截断，此时个别详情失败不可能让整批不完整。
- **错误率的分母是「本轮请求目标量」**（关键词数 × 每词上限），不是库内总条目。
  这条规则被真机数据推翻过两次，记录在此以免重蹈：
  1. 初稿用「错误行 / 库内条目数」—— 分母是历史归档，会随存档增长而稀释：5000 条的
     归档里一次半失败批次只算出 2%，照样被判「完整」。
  2. 改为绝对条数后**仍不是尺度无关**：同一失败率（7.5%）在 120 条批次判 high、在
     185 条批次判 low，只因为绝对错误数分别落在阈值 10 的两侧。
  现版本以本轮目标量作分母，尺度无关性由参数化回归测试钉死。
- `notes_new == 0` **不算 low**：重复运行同一关键词时 0 新增是正常的，不是失败信号。
- 报告头部显式声明整批是否完整。**个别条目失败只列明细，不否定整批。**
- 采集期的任何异常都必须被转成结果对象记录在案，不得让本轮没有报告，也不得留下孤儿 `running` 行。

### Q3 可版本化：词表/提示词升级后新旧可区分

**实现方式**：`analysis_version = hash(提示词模板 + 词表 + 模型 id + 打分公式版本)`。

- 每次分析写入该版本号；升级产生新行，**不覆盖**旧行。
- `score_formula_version` 独立版本化，公式调整后新旧排名可区分。
- 报告声明本次使用的版本。

## 5. 口径

`转播量` 按「综合传播/互动表现（以转发为主，含点赞、收藏、评论）」统一理解，不再单独拆分。

打分公式（v1）：

```
raw = 5×share + 3×collected + 2×comment + 1×liked
composite = log1p(raw)
```

取 `log1p` 压制的理由：避免单条爆款在跨帖子比较中压倒其余样本。原始 `raw` 同时落库，便于口径复核。

## 6. 关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 与爬虫的接缝 | **SQLite 库表**，非爬虫对象 | 爬虫必定拉起浏览器并走登录；以库表为缝可让分析层完全免登录、可离线回归 |
| 爬取触发方式 | 子进程调用既有 `main.py` | 隔离浏览器/登录生命周期；失败时存档仍在（R6） |
| 存档后端 | **SQLite** | CSV/JSON/JSONL 后端不做去重，会破坏 R5「同一内容不重复分析」 |
| 博主信息 | 从已采集帖子聚合 | 仓库已刻意删除创作者档案表并匿名化 `user_id`（`database/models.py:19-25`）。不新增身份采集，尊重既有隐私设计 |
| 分析后端 | 接口 + `NullAnalyzer` | 当前 CLI 无凭据、无 API Key。R6 本就要求模型可缺席 |
| 评估模式 | `code-only` | 边界明确不做 WebUI |

## 8. 已确认的既有数据陷阱

1. 互动数经 `str(...)` 落库（`store/xhs/_store_impl.py:151-154`），**缺失值为字符串 `"None"`**。
2. 互动数可能带中文单位（`"1.2万"`、`"1亿"`），须解析为整数。
3. `image_list` / `tag_list` 是 `json.dumps` 字符串，可能为 `"null"`。
4. `XhsNote.note_id` **无唯一约束**（仅索引），并发下可能重复；趋势侧须自行约束。
5. `get_session()` 对 `json/csv/jsonl` 返回 `None`，趋势层须显式要求 DB 后端。

## 10. 前置条件与风险

- **实测需一次性地登录小红书**。`crawler.start()` 必定走登录流程；`browser_data/` 登录态失效时需扫码。这是唯一无法由开发方单方完成的前置条件。
- **GAN 评估器无法自行跑真实爬取**（无登录态）。因此切片 1 配套录制 fixture，使全链路在无登录、无网络、无模型时可回归 —— 同时满足 R6「可复跑」。

## 11. 不可信输入与并发（切片 1 加固）

爬取到的标题/标签/昵称/URL 均来自第三方平台，属不可信输入；`platform`、`output_dir`
则来自命令行。据此加固：

| 面 | 处理 |
|---|---|
| `platform` 进库与进文件名 | 在写入任何数据之前 `validate_platform()` 白名单校验；`rebuild_report` 路径同样受约束 |
| 标题/标签/昵称渲染 | `_cell()` 转义 `\ [ ] ( ) < > \|`，阻止 `](` 撑破链接语法、阻止尖括号被当成 HTML 标签 |
| `note_url` 渲染 | `_safe_url()` 只放行 http/https，挡掉 `javascript:`/`data:`；括号百分号编码 |
| 命令拼接 | argv 列表传入 `subprocess.run`，无 `shell=True`，关键词不经过 shell 解析 |
| SQL | 全部走 SQLAlchemy 表达式，无字符串拼接 SQL |
| 匿名化 | 沿用上游已脱敏的 `nickname` 与已哈希的 `creator_hash`，不重新引入原始 user_id |
| 同批次重复 `note_id` | 落库前按 `(platform, note_id)` 去重 —— `xhs_note.note_id` 无唯一约束，重复行会让 flush 撞唯一约束、整笔回滚 |
| 无 `note_id` 的行 | 直接丢弃（无 id 无法追踪同一内容） |

**已知限制**：落库沿用仓库既有的「先查后写」风格，两个 `trend run` 进程并发跑同一批
数据时存在竞态，双方都判定为不存在而同时 INSERT。本地 CLI 串行使用不触发；真正并发
安全需 `ON CONFLICT` / `MERGE` 这类方言相关 upsert，留待后续切片。
